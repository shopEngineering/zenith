# Running HuggingFace models on gpu-node (and testing them from ZENITH)

**TL;DR — you're already doing it.** gpu-node serves the HuggingFace model
`Qwen/Qwen2.5-7B-Instruct` with vLLM; ZENITH talks to it as the provider `gx10vllm`.
A test chat through the whole path (laptop → gpu-node → model) answers in ~4s. Nothing
runs on your laptop — gpu-node does all the GPU work; ZENITH is just the remote control.

```
Your laptop                          gpu-node (GB10, 121 GB)
┌───────────────┐   OpenAI API      ┌────────────────────────────┐
│ ZENITH UI     │ ───────────────▶  │ vLLM  :8000                 │
│ provider:     │  LAN <gpu-host>│   serves a HuggingFace model│
│ "gx10vllm"    │  or Tailscale     │   Qwen/Qwen2.5-7B-Instruct  │
└───────────────┘  <tailscale-host>     └────────────────────────────┘
```

## What a "HuggingFace model" actually is

HuggingFace Hub is a registry of open models. Each has an **ID** like
`Qwen/Qwen2.5-7B-Instruct` or `meta-llama/Llama-3.1-8B-Instruct` — that ID points at
the weights + config + tokenizer. You don't "install" a model; a serving engine
(here, **vLLM**) downloads it by ID on first use and exposes an **OpenAI-compatible
API**. Because it's OpenAI-shaped, ZENITH treats it exactly like any other provider.

- **Open models** (Qwen, Mistral, Llama, Gemma, Phi…) — pull by ID, run on gpu-node.
- **Gated models** (most Llama, some others) — accept the license on the model's HF
  page once, then pass an **HF token** so the download is authorized (below).

## Use a *different* model on gpu-node

Everything happens on gpu-node. SSH in and restart the vLLM container with a new model
ID. This is the exact command that's running now — only two things change:

```bash
docker rm -f zenith-vllm 2>/dev/null    # stop the current model

docker run -d --name zenith-vllm --restart unless-stopped \
  --gpus all --ipc=host --ulimit memlock=-1 --ulimit stack=67108864 \
  -p 8000:8000 \
  -v /home/me/.cache/huggingface:/root/.cache/huggingface \
  nvcr.io/nvidia/vllm:26.01-py3 \
  vllm serve Qwen/Qwen2.5-14B-Instruct \       # ← 1. the HuggingFace model ID
    --host 0.0.0.0 \
    --served-model-name qwen2.5-14b \          # ← 2. the short name ZENITH shows
    --max-model-len 8192 \
    --gpu-memory-utilization 0.85
```

- **① model ID** — any HuggingFace ID. First run downloads the weights (cached under
  `~/.cache/huggingface`, so later restarts are fast).
- **② served-model-name** — the short label you'll pick in ZENITH's model dropdowns.
- **Gated model?** add `-e HF_TOKEN=hf_xxx` to the `docker run` (get the token at
  huggingface.co → Settings → Access Tokens, and click "Agree" on the model page first).
- **First load** takes ~1–3 min (download + weight load); `docker logs -f zenith-vllm`
  shows progress. vLLM is reboot-persistent (`--restart unless-stopped`).

No ZENITH change is needed for a same-endpoint swap — the `gx10vllm` provider points
at `:8000` regardless of which model is loaded; just pick the new `served-model-name`
in the UI. (To run several models at once, start more containers on other ports and
add a provider per port.)

## What fits on the 121 GB GB10

vLLM needs room for weights **plus** KV-cache. Rough fp16 footprint (÷2 with 4-bit
AWQ/GPTQ quantization):

| Model size | fp16 weights | Fits? | Notes |
|-----------:|-------------:|:-----:|-------|
| 7B  | ~14 GB | ✅ easily | current default; fast |
| 14B | ~28 GB | ✅ | great quality/speed balance |
| 32B | ~64 GB | ✅ | strong; leave KV headroom (`--max-model-len`) |
| 70B fp16 | ~140 GB | ❌ | too big at fp16 |
| 70B AWQ/GPTQ 4-bit | ~40 GB | ✅ | use a `-AWQ`/`-GPTQ` model ID |

> The 35B **NVFP4** attempt is a known blocker — the vLLM build's weight loader
> crashes on that checkpoint (`KeyError w2_input_scale`). Prefer a standard fp16 or
> AWQ/GPTQ model until that's sorted. See the roadmap.

## Run tests with the model — three ways, all in ZENITH

Once served on gpu-node, the model is a **provider** ZENITH can call. Providers plug in at:

1. **Models · chat** — open the provider (e.g. `gx10vllm`), pick the model, and talk to
   it. Fastest sanity check on a freshly-loaded model; open two chat windows for a manual
   side-by-side. (vLLM streams tokens; Ollama chats also get a ⏱ STATS toggle.)
2. **Loops (provider runner)** — schedule a recurring call to the model (a loop whose
   runner is set to a *provider*, not a coding CLI) — e.g. a nightly digest generated by
   the gpu-node model.
3. **Scripted / API comparison — the real "bake-off two models" path.** Send the same
   prompt(s) to N provider models via `POST /api/chat` (`{"stream": false}` → `{"text"}`),
   record answer + latency, and have a judge (Claude, or a stronger model) rank them.

> **Important — what the A/B app is *not* for here.** ZENITH's **A/B · Compare** dock app
> and **Ops · Jobs** runner drive **coding agents** (`claude` / `codex` / `aider`) through
> `spawn_job` — they're for comparing *agents*, and they do **not** take a raw vLLM/Ollama
> provider model as an arm or backend. So a vLLM-vs-vLLM comparison (like 7B vs 14B) runs
> through the **provider path** above (Models chat, or the scripted `/api/chat` route),
> **not** the A/B app. (You *can* pull a local model into the agent-based A/B by pointing
> `aider`/`codex` at the vLLM OpenAI endpoint via their own config, but that's not wired by
> default.)

## Try this next

1. On gpu-node, serve `Qwen/Qwen2.5-14B-Instruct` (served-model-name `qwen2.5-14b`) on a second
   port **alongside** the 7B (so both are live at once), and add it as a second provider.
2. Send the same prompt(s) to `qwen2.5-14b` and `qwen2.5-7b` via `/api/chat`, then compare
   answer quality + latency — a judge tells you whether 14B earns its extra latency for
   your prompts. (This is exactly the bake-off `scratchpad/bakeoff.py` runs.)

That's the whole loop: pick a HuggingFace ID → serve it on gpu-node → compare it via the
provider path in ZENITH — all without anything heavy touching your laptop.

## Recommended models for gpu-node (bake-off results, 2026-07-17)

The GB10 has huge capacity (121 GB) but modest bandwidth (~273 GB/s), so the winners are
**large MoE + 4-bit** (many total params for quality, few *active* params for speed). Verified
by a 7B/14B/35B/80B bake-off through the provider path:

- **★ Best daily driver — `RedHatAI/Qwen3-Next-80B-A3B-Instruct-NVFP4`** (80B total / 3B active,
  `compressed-tensors`, ~48 GB). Correct + **3–30× faster** than the others (Instruct model, answers
  directly). Serve on the `vllm/vllm-openai:cu130-nightly` image (`--trust-remote-code`,
  `--gpu-memory-utilization 0.85` solo).
- **Precision / reasoning — `RedHatAI/Qwen3.6-35B-A3B-NVFP4`** (35B / 3B, `compressed-tensors`). Slower
  (emits `<think>` traces) but its deliberation wins on strict-precision tasks (exact word counts) where
  the fast 80B miscounts. Add `--reasoning-parser qwen3` for prod.
- **Fast/simple — Qwen2.5-7B / 14B** (fp16). Hold their own on everyday reasoning/code.

**⚠️ Format matters more than size on this box.** Prefer **`compressed-tensors`** (or FP8 / AWQ / GPTQ-Int4)
quants — they use kernels that run correctly on the GB10's SM121 GPU. **Raw MXFP4 / raw `nvidia`-NVFP4 builds
produce *garbage* output on SM121** (a known FP4-kernel defect). Concretely: **`openai/gpt-oss-120b` does NOT
work here** — it loads and serves, but its MXFP4 weights yield malformed output even with the
`VLLM_MXFP4_USE_MARLIN=1` workaround. Always **sanity-check a new model answers a known question correctly**
before trusting it. (gpt-oss may work via llama.cpp/ollama — a different runtime — but not vLLM on SM121.)

## Throughput benchmark (2026-07-19) — the big models are the *fast* ones

Each model benchmarked solo (full box) with a 1→128 concurrent-request sweep, 128-token replies. **Zero
failures** at any level. Key numbers:

| Model | Quant | Single-stream tok/s | Peak aggregate tok/s | Batch multiplier |
|-------|-------|--------------------:|---------------------:|-----------------:|
| Qwen2.5-7B | fp16 dense | 12.8 | **1170** (@128) | 91× |
| Qwen2.5-14B | fp16 dense | 8.0 | 656 (@128) | 82× |
| Qwen3.6-35B-A3B | NVFP4 MoE | **39.8** | 910 (@128) | 23× |
| Qwen3-Next-80B-A3B | NVFP4 MoE | 36.5 | 985 (@128) | 27× |

**The counterintuitive result: single-stream speed is *inverted* vs size.** The 35B/80B (4-bit MoE, 3 B
active) answer a single chat **~3–5× faster** than the 7B/14B (fp16 dense). On a bandwidth-bound box, decode
speed ∝ 1 / (active-params × bytes-per-param): 7B fp16 ≈ 14 GB/token vs 35B-A3B NVFP4 ≈ 1.5 GB/token — the
"35B" is ~10× lighter *per token*. **So for snappy single-user use, pick the sparse quantized model, not the
small dense one.** Under concurrency the box is a batching machine (dense models amortize their weight reads →
82–91× scaling; the 7B tops out at 1170 tok/s); all four were still climbing at 128 (ceiling is beyond 128, no
plateau, no drops). Practical: **80B/35B for snappy single-user, 7B for max multi-user throughput; avoid 14B
fp16 for speed** (slowest single-stream + lowest peak). Harness: `nohup` on gpu-node; each model solo at full box.
